# Tailscale configuration

My [Tailscale](https://tailscale.com) tailnet (`bensoyka6@gmail.com`, MagicDNS suffix
`broadbill-gecko.ts.net`). This directory is a [Terraform](https://developer.hashicorp.com/terraform)
root module that manages the tailnet's access-control policy, DNS configuration, tailnet-wide
settings, and the per-device configuration that Terraform is able to reach.

## Layout

| File | Contents |
| --- | --- |
| `versions.tf` | Terraform and provider version constraints |
| `backend.tf` | S3 remote state (`bsoyka-tfstate/infra-tailscale.tfstate`) |
| `providers.tf` | Tailscale provider |
| `locals.tf` | Tailnet name, MagicDNS suffix, and the device map |
| `devices.tf` | `tailscale_device` data source for each device in the tailnet |
| `acl.tf` | The tailnet policy file, as HCL objects rendered with `jsonencode` |
| `dns.tf` | MagicDNS, nameservers, and search paths |
| `settings.tf` | Tailnet-wide settings (device approval, key duration, HTTPS, ...) |
| `device-*.tf` | One file per device that has managed configuration: its tags, enabled subnet routes, and key expiry |

Devices with no managed configuration appear only in `locals.tf` and `devices.tf`.

## What Terraform doesn't manage

- **Route advertisement.** `--advertise-routes` / `--advertise-exit-node` are device-side flags.
  `tailscale_device_subnet_routes` only chooses which *advertised* routes are enabled.
- **Device enrollment.** Devices join the tailnet out of band; Terraform adopts them via
  `data.tailscale_device` and configures them. It never creates or removes one.
- **Shared-in nodes.** `homeassistant.tail5062cf.ts.net` is shared in from a different tailnet
  (a different owner and MagicDNS suffix). It shows up in `tailscale status` but only its owner
  can configure it, so it's absent from `locals.tf` entirely.
- **The API credential itself.** Created by hand in the admin console, so Terraform can't lock
  itself out.

## Prerequisites

- `terraform`, pinned in the repo's `mise.toml` -- run `mise install`
- AWS credentials with read/write on `s3://bsoyka-tfstate` (for state)
- A Tailscale API access token, exported as `TAILSCALE_API_KEY`, plus `TAILSCALE_TAILNET=-`

Settings → Keys → OAuth clients isn't available on this account, so this module authenticates with
a personal API access token instead of an OAuth client. The tradeoff: a token expires (90 days max)
and has to be rotated by hand, where an OAuth client wouldn't. The token inherits whatever
permissions the account that created it has, so it needs to be generated by an account with
Owner/Admin access to the tailnet.

Credentials are set locally via [direnv](https://direnv.net) in the repo's `.envrc`, which is
gitignored.

## Usage

```sh
cd tailscale
terraform init
terraform plan
terraform apply
```

There is no CI pipeline -- plans and applies run locally.

## Notes

- The admin console's policy editor is read-only because `acls_externally_managed_on` is on.
  Policy changes go through a PR here, then `terraform apply`.
- The policy file is stored as HCL objects passed through `jsonencode`, not as HuJSON. The
  Tailscale API's JSON validation rejects HuJSON's `//` note-key convention (`400: json: unknown
  field "//"`), so there's no way to leave a "managed by Terraform" marker inside the policy
  itself -- the comment on `tailscale_acl.this` in `acl.tf` is the only place that's recorded.
  Comments from the original policy live as `#` comments near what they described; the rendered
  policy in the admin console has none and sorts keys alphabetically.
- `tailscale_acl` replaces the *entire* policy on every apply. `reset_acl_on_destroy` is left at
  its default `false` so a `terraform destroy` doesn't reset the tailnet to the default allow-all
  policy.
- The policy has no `autoApprovers` block. If one is ever added for a route that
  `tailscale_device_subnet_routes` also manages, the two will fight: Terraform disables a
  non-declared route, the device re-advertises it, autoApprovers re-enables it, and the next plan
  shows drift forever. Keep autoApprovers and explicit route management mutually exclusive.
- `townhall` is a tagged device (`tag:prod`, `tag:server`), so its key already never expires; it
  deliberately has no `tailscale_device_key` resource, since tagged devices reject attempts to
  change that setting. `postoffice` is untagged with expiry explicitly disabled, so it genuinely
  needs one.
- Applying tags to a currently-untagged device is a one-way door -- ownership transfers to
  `tagged-devices` and key expiry is disabled for it.
- A device leaving the tailnet breaks `plan` for the entire module, since its `data.tailscale_device`
  lookup fails. Retiring a device means removing it from `local.devices` and running
  `terraform state rm` on its resources in the same change.
- Auth keys, webhooks, contacts, and OAuth clients are deliberately out of scope.
